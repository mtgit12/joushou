## 1. プロダクト概要

### 1.1 名称

城将（じょうしょう）※仮称

### 1.2 一言でいうと

日本地図から城を探して訪問記録を残せ、城にゆかりのある戦国武将の情報まで調べられる、城めぐりと歴史好きのためのWebサービス。

### 1.3 背景

- 日本100名城や推し武将にゆかりのある城を、地図上で一覧したい。
- 行ったことのある城を記録し、地図上で振り返りたい。
- 有名・無名を問わず、記録に残る戦国武将の情報を一か所で調べられるようにしたい。

---

## 2. ターゲットユーザー

### 2.1 主なユーザー

- 城めぐりが趣味の人
- 歴史（特に戦国時代）が好きな人

### 2.2 利用シーン

- 旅行先を検討するとき、または旅行先の近くに城がないか確認するとき
- 趣味の時間や空き時間に、スマホやPCのブラウザでゆっくり眺めるとき
- 歴史小説の執筆やゲームプレイの参考資料を探すとき

---

## 3. 解決する課題と提供価値

### 3.1 課題（要確認）

- 城の情報はテキスト中心の一覧が多く、位置関係や周辺の城を把握しにくい。
- 有名でない武将の情報は各所に散らばっており、まとめて調べにくい。
- 城めぐりの記録を、地図上で振り返ったり人に見せたりする手段が少ない。

### 3.2 提供価値（差別化ポイント）

- 城の一覧をテキストではなく2Dマップで見られる。
- 有名・無名に関わらず、戦国武将の情報を検索・閲覧できる。
- 城と武将のつながり（城主、築城、生誕地など）をたどれる。
- 訪問した城を地図上に記録し、公開プロフィールで人に見せられる。
- 城好き・歴史好きのユーザーからの情報提供によって、データが育っていく。

## 4. プロジェクトの目的

このプロジェクトは、プロダクトとしての価値と同時に、オーナー自身の学習とポートフォリオを目的としています。

### 4.1 学習目標

| 分野 | 学びたいこと | 第一フェーズでの扱い |
|---|---|---|
| フロントエンド | Next.js でのフルスタック開発 | 対象 |
| バックエンド | Laravel への DDD 導入 | 対象 |
| バックエンド | Go での開発経験 | 第二フェーズ（既存機能の一部を Go に切り出す） |
| 認証 | 認証の実装（Auth0 との連携、トークン検証、権限管理） | 対象 |
| インフラ | AWS でのインフラ構築 | 対象（低コスト構成から始める） |
| 品質 | テスト自動化（Unit テスト、E2E テスト、CI） | 対象 |
| 開発プロセス | 仕様駆動開発（SDD）の実践 | 対象 |

### 4.2 ポートフォリオとしての狙い

Web系企業の採用担当者や現在の所属会社の上司に対して、**設計から運用までを一人でやり切れること**を示す。

そのため、動くプロダクトだけでなく、仕様・設計ドキュメント、テスト、CI/CD、運用の仕組みまでをリポジトリで公開する。

## 5. 第一フェーズのゴール

### 5.1 完了の定義

以下をすべて満たした時点で、第一フェーズ完了とする。

1. `requirements.md` の優先度 Must の要件がすべて実装されている。
2. 本番環境に公開され、誰でも会員登録できる状態になっている。
3. 利用規約とプライバシーポリシーが公開されている。
4. 身近な人に実際に使ってもらい、レビューを受けられる状態になっている。

### 5.2 スケジュール

| 項目 | 内容 |
|---|---|
| 目標期間 | 6か月 |
| 最長期間 | 12か月（これを超えそうな場合は、スコープを削って公開を優先する） |
| 稼働時間 | 平日1〜2時間、週末3〜4時間 |

マネジメント経験を積むことも目的の一つとし、`tasks.md` で計画と実績の差を記録して、見積もりの精度を上げていく。

## 6. スコープ

### 6.1 第一フェーズでやること

- 2Dマップ上に城をピンで表示する。
- 城・戦国武将の検索付き一覧と詳細を表示する。
- 会員登録・ログイン（メールアドレス＋パスワード、Googleログイン）。
- 会員が訪問した城を記録し、公開プロフィールで見せられる。
- 会員が推し武将を1名登録できる。
- 会員が城・武将の新規情報や修正を提供でき、管理者が審査してから反映する。
- ユーザー向け機能に対応した管理画面（城・武将データ管理、情報提供の審査、CSV入出力、ユーザー管理）。
- システム内通知とメール通知。
- スマホブラウザでの利用（スマホ優先のレスポンシブ対応）。

### 6.2 第一フェーズでやらないこと

- 合戦情報の追加
- 年代ごとの勢力図表示（年代スライダーで大名家の支配地域を色分けする機能）
- 歴史小説に関連する機能
- ネイティブアプリ化（iOS / Android アプリ）
- 決済機能（サブスクリプション）
- 「行きたい城」の登録
- 推し武将のゆかりの城を地図上でハイライトする機能
- ユーザー同士のやりとり（掲示板、コメント、フォロー、いいね）
- 多言語対応
- Go によるバックエンド開発

### 6.3 第二フェーズ以降の候補

- 合戦情報の追加
- 年代ごとの勢力図表示
- 「行きたい城」の登録
- 推し武将のゆかりの城のハイライト表示
- 掲示板機能
- 一部機能の Go への切り出し
- 決済機能（Stripe）
- 城・武将データの拡充（100名城以外の城、武将の追加）

上記以外の技術は原則として採用しない。追加が必要な場合は、理由を `architecture.md` に記録してから採用する。

### 7.2 インフラの方針

- 第一フェーズは**費用を優先**し、AWS 上で小さなサーバーに集約するなど低コストな構成から始める。
- 利用者が増えた時点で、コンテナ実行環境やマネージドDBへの分離など、段階的に拡張する。
- 拡張しやすいように、アプリケーションは Docker 化し、設定は環境変数で切り替えられるようにする。
- 具体的な構成は `architecture.md` で決める。

## 8. 開発原則

### 8.1 優先順位

迷ったときは、次の順で判断する。

1. **学習**：新しい技術や設計手法に挑戦することを優先する。
2. **速度**：期限内に公開することを優先し、作り込みすぎない。
3. **品質**：上記を満たしたうえで品質を高める。

ただし、次の2点は優先順位に関係なく必ず守る。

- **セキュリティと個人情報の保護**：誰でも登録できる公開サービスであり、ソースコードも公開しているため。
- **最低限のコード品質**：Biome のチェックと CI が通らないコードはマージしない。

### 8.2 大事にすること

- **ユーザビリティ**：初めて訪れた人が、説明を読まなくても地図と検索を使えること。
- **アクセシビリティ**：WCAG 2.2 レベル AA を目標とする。地図を操作できない人でも、一覧と検索で同じ情報にたどり着けるようにする。
- **継続的な運用**：作って終わりにせず、自分一人で無理なく運用し続けられる仕組みにする。
- **きれいなコード**：DDD の考え方に沿って責務を分け、読みやすいコードを書く。

### 8.3 仕様駆動開発のルール

- 実装の前に、必ず `docs/specs/` に機能仕様を書く。
- 仕様を変えるときは、先にドキュメントを更新してから実装を変える。
- `requirements.md` の受け入れ基準と、テスト・機能仕様を対応付ける。

### 8.4 AI エージェントの利用

- AI エージェント（Claude Code など）に実装を任せてよい。
- ただし学習が最優先のため、**AI が書いたコードも、自分で説明できる状態になってからマージする**。
- AI には `docs/` 配下のドキュメント（特に `conventions.md` と該当する機能仕様）を必ず渡す。

### 8.5 テスト

- Unit テストと E2E テストを書く。作成の大部分は AI に任せてよい。
- ドメインロジック（Laravel の DDD におけるドメイン層）は Unit テストを必須とする。
- 主要なユーザーの流れ（城を探す、訪問記録を登録する、情報提供する、審査する）は E2E テストで確認する。
- テストは CI で自動実行する。

### 8.6 公開リポジトリとしての注意

- ソースコードは GitHub で公開する。
- API キー、パスワード、接続情報などの秘密情報は、リポジトリに含めない。
