# Linear Issue の作成（城将）

城将の作業はすべて Linear の Issue から始まり、ブランチ名・コミット・PR が Issue 番号で紐づく（`docs/conventions/branch-commit.md`）。Issue は「後から読んで何をすれば完了か分かる」状態で作ることが大事になる。

ユーザーは複数の Issue をまとめて依頼することが多い。下書きの確認は求めず、内容を組み立てたらそのまま作成し、作成後にまとめて報告する。

## 固定の値

| 項目 | 値 |
|---|---|
| チーム | `TAK`（Takuro） |
| プロジェクト | `城将（じょうしょう）※仮称`（`P-TAK-3`） |
| 担当者 | `me` |
| ステータス | `Todo`（ユーザーが指定したときだけ変える） |
| 優先度 | `Medium`（3）（ユーザーが指定したときだけ変える） |
| 期日（Due Date） | 空欄（ユーザーが指定したときだけ入れる） |

期日はこのプロジェクトで見積もりの役割を持ち、ユーザーが着手のタイミングで自分で決める。（見積もり（Estimate）の項目は使わない。）

## 手順

### 1. 依頼内容を把握する

依頼から、Issue ごとに次を読み取る。

- 何を、なぜ行うか
- 種類（新機能・不具合・改善・ドキュメント・リファクタリング・テスト・雑務・CI）
- 対象（フロントエンド・API・DB・インフラ）

確認なしで作成するので、推測すると Issue の中身が大きく変わってしまう点（対象の画面が特定できない、何をすれば完了か分からないなど）があるときだけ、作成前に質問する。細かい点は推測で埋め、報告のときに伝える。

依頼が機能仕様・ユーザーストーリー・画面に関係する場合は、関連 ID を正しく書くために該当箇所を読む。ID を推測で書くと、後で Issue から仕様をたどれなくなるため。

| 知りたいこと | 読むもの | ID の形式 |
|---|---|---|
| 機能仕様のファイル | `docs/specs/index.md` | `docs/specs/NNN-xxx.md` |
| ユーザーストーリー・受け入れ基準 | `docs/requirements.md` | `US-xx`、`AC-xx-n` |
| 画面 | `docs/design/screens.md` | `P-xx`（一般）、`M-xx`（会員）、`A-xx`（管理） |
| シナリオ・業務ルール | 該当する機能仕様書 | `SC-NNN-nn`、`BR-NNN-nn` |

見つからない ID は書かずに空けておき、報告のときに伝える。

### 2. Issue の構成を決める

1つの Issue は1つのブランチ・1つの PR で終わる大きさにする（PR の差分は 400 行程度が目安。`branch-commit.md` 4.4）。

**フロントエンドの新規画面**は、1画面を親 Issue にして、次の3つの子 Issue に分ける。子 Issue には実施順に `blockedBy` を付ける（モック → テスト → API連携）。

| 子 Issue | 内容 |
|---|---|
| モック | `openapi.yaml` を書き、Apidog のモックサーバー（仮 API）に BFF（Server Actions）からつないで画面を作る |
| テスト | モックサーバーにつないだ画面の Unit テスト（Vitest）の作成・実施 |
| API連携 | Laravel の API ができたあと、接続先を Laravel に切り替えて動作を確認する |

フロントエンドは Laravel より先に作るため（`docs/architecture.md` 9.4）、Laravel を待つ作業は API連携に分けておく。そうすると、モックとテストは Laravel の進み具合に関係なく終えられる。

API連携には、対応する Laravel の API 実装 Issue への `blockedBy` も付ける。`list_issues` で TAK の既存 Issue（タイトルや画面名・API 名）から探し、見つからなければ付けずに報告で伝える。

E2E テスト（Playwright）はこの子 Issue に含めない。別のタスクとして扱うので、ユーザーに依頼されたときだけ作る。

それ以外（既存画面の修正、API の実装、不具合、ドキュメントなど）は、親子に分けず1つの Issue で作る。大きすぎる場合は、同じ階層の Issue に分けて作る。

### 3. 各 Issue の中身を決める

#### タイトル

- 日本語で、何をするかが一目で分かる短い文にする（目安 30 文字以内）。
- フロントエンドの新規画面は、親を `[画面名]画面の作成`、子を `[画面名]画面 / モック`、`[画面名]画面 / テスト`、`[画面名]画面 / API連携` にする。画面名は `docs/design/screens.md` の表記に合わせる。
- 不具合は「〜が〜になる」のように現象を書く。

#### ラベル

種類のラベルを1つと、対象のラベルを必要なだけ付ける。

| 種類 | ラベル | 対応するブランチの種類 |
|---|---|---|
| 新機能 | `feature` | `feature` |
| 不具合 | `bug` | `fix` |
| 既存機能の改善 | `improvement` | `feature` |
| ドキュメントのみ | `documentation` | `docs` |
| 振る舞いを変えない整理 | `refactor` | `refactor` |
| テストのみ | `test` | `test` |
| 依存・設定の更新 | `chore` | `chore` |
| CI/CD・ビルド | `build` | `ci` または `chore` |

対象のラベル：`frontend`、`api`、`database`、`infrastructure`、`migration`、`security`

フロントエンドの新規画面の子 Issue「テスト」は、種類を `test` にする。

#### 本文

種類に応じた雛形を `references/templates.md` から選んで埋める。雛形の見出しは変えない（Issue 同士で同じ場所に同じ情報があると、後から比較・振り返りしやすいため）。該当しない作業内容の行は消す。

### 4. 作成する

`save_issue` で作成する。親子関係がある場合は親を先に作り、子の `parentId` に親の ID を入れる。`blockedBy` は、先に作った Issue の ID を指定する。Linear のテンプレート（`template` 引数）は使わない。テンプレートの本文や子 Issue が混ざり、この構成と食い違うため。

### 5. 報告する

作成した Issue を表にまとめて報告する。

| ID | タイトル | ラベル | 親 | ブランチ名 |
|---|---|---|---|---|
| TAK-15 | 城詳細画面の作成 | feature, frontend | － | － |
| TAK-16 | 城詳細画面 / モック | feature, frontend | TAK-15 | `feature/tak-16` |

- ブランチ名は `branch-commit.md` 2.2 の形式（`<ブランチの種類>/tak-<番号>`）で示す。Linear の「Copy git branch name」の値は使わない。作業は子 Issue で行うので、親 Issue のブランチ名は書かない。
- 表のあとに、Linear の URL（親、または1件目）と、推測で埋めた点・見つからなかった関連 ID・期日が空欄であることを短く添える。
