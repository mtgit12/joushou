# フロントエンドの Unit テスト（Vitest ＋ React Testing Library）

このスキルでは、`docs/specs/` の機能仕様書に書かれた振る舞いを、`apps/web` の Unit テストとして書く。テストの目的は「仕様どおりに動くこと」を確かめることであり、実装をなぞることではない。だから、テストの観点は**仕様書から取り**、実装コードは「どこをどう呼べば確かめられるか」を知るために読む。

## 判断の基準

- **仕様書が正**。実装が仕様と違う動きをしていたら、テストは仕様どおりに書き（＝失敗する）、実装は直さずに報告する。実装を直すかどうかはユーザーが決める。
- **仕様書がなければ書かない**。テストの根拠がないまま実装から観点を起こすと、今の動き（バグも含めて）を固定するだけのテストになるため。
- **追加のパッケージは使わない**。`@testing-library/user-event` と `@testing-library/jest-dom` は導入しない方針。操作は `fireEvent`、確認は Vitest 標準の `expect` で書く（書き方は `references/patterns.md`）。

## 手順

### 1. 依頼を把握する

依頼から対象を特定する。

| 依頼の形 | 対象の特定のしかた |
|---|---|
| 画面 ID（例：A-02、P-05） | `docs/design/screens.md` で画面の行を探し、関連する機能を確認する。`docs/specs/index.md` で、その画面 ID を含む機能仕様書を探す。実装は `apps/web/src/features/` から該当する機能ディレクトリを探す |
| ファイル／ディレクトリのパス | そのファイル（ディレクトリならテスト対象になるファイル全部）。機能ディレクトリ名と `docs/specs/index.md` から対応する機能仕様書を探す |

### 2. 仕様書を確認する

対応する `docs/specs/NNN-<機能名>.md` を読む。

- **仕様書が存在しない**（`index.md` で ☐ のまま、またはファイルがない）場合は、ここで作業を止め、ユーザーに「仕様書がないためテストを書けない」ことと、どの仕様書（番号・ファイル名）が必要かを伝える。推測でテストを書き始めない。
- **ステータスが「下書き」**の場合は、そのまま進めてよいかユーザーに確認する。下書きの仕様は変わる可能性が高く、テストも書き直しになるため。

仕様書のうち、次の2つをテストの観点にする。

| 仕様書の章 | テストにするもの |
|---|---|
| 6章 受け入れ基準 | 「テスト」列が **Unit** の行。E2E の行は対象外（Playwright で別に書く） |
| 3章 入力とバリデーション | 各項目の制約。必須・最大／最小・形式などを zod スキーマのテストにする。**境界値はちょうどの値と1つ外の値の両方**を確かめる（例：500文字は通る、501文字はエラー） |

ほかに読むもの（全文でなく該当箇所だけでよい）：

- `docs/conventions/React-Nextjs.md` 14章（テストの規約）、8章（フォーム）、7.4（`ActionResult` 型）
- `docs/architecture.md` 2.4（何を Vitest で、何を E2E で確かめるか）
- `docs/glossary.md`（テスト名に使う用語）

### 3. テスト対象のファイルを洗い出す

`architecture.md` 2.4 に従い、次だけを Vitest の対象にする。

| 対象 | 置き場所の例 | テストする |
|---|---|---|
| zod スキーマ | `features/*/schemas.ts` | ○ |
| ユーティリティ関数 | `lib/utils/`、`features/*/` 内の関数 | ○ |
| カスタムフック | `features/*/hooks/` | ○ |
| クライアントコンポーネント（`"use client"`） | `features/*/components/` | ○ |
| 非同期の Server Components | `page.tsx`、`async function` のコンポーネント | ×（E2E で確かめる） |
| 地図（MapLibre） | `components/ui/map.tsx` など | ×（jsdom では WebGL が動かない） |
| `components/ui/` の shadcn/ui の部品そのもの | `components/ui/` | ×（CLI が生成したもの。使う側のテストで確かめる） |

受け入れ基準の各行が、どのファイルのテストで確かめられるかを対応づける。対応するファイルが見つからない行（未実装や、Unit では確かめられない行）は、報告の「書けなかった受け入れ基準」に回す。

### 4. テストを書く

書き方の例（スキーマ、フォーム、フック、モック）は `references/patterns.md` にまとめてある。書き始める前に目を通すこと。特に間違えやすい点は次のとおり。

**規約（React-Nextjs.md 14章）**

- テストファイルは対象の隣に、`対象のファイル名.test.ts(x)` で置く。
- `describe` に対象の名前（コンポーネント名・関数名・スキーマ名）、`it` に確かめる振る舞いを**日本語**で書く。
- 受け入れ基準から作ったテストは、`it` の先頭に SC の ID を付ける（例：`it("SC-008-03 未来の日付は登録できない", ...)`）。仕様書と結びつけるため。3章の境界値から作ったテストには ID は付けない。
- 1つの `it` で確かめることは1つ。準備・実行・確認（Arrange / Act / Assert）の順に書く。
- 要素は `getByRole` → `getByLabelText` → `getByText` の順で探す。`getByTestId` は最後の手段。
- スナップショットテストは使わない。

**このリポジトリの設定による注意**

- `vitest.config.mts` で `globals` を有効にしていないため、`describe`・`it`・`expect`・`vi` は `vitest` から import する。また React Testing Library の自動クリーンアップが働かないので、コンポーネントのテストでは `afterEach(cleanup)` を書く（書かないと前のテストの DOM が残り、要素が複数見つかって失敗する）。
- `tsc --noEmit` はテストファイルも検査する。テストでも `any`・非 null アサーション（`!`）は使わない。`getBy*` は見つからなければ例外を投げるので、`!` なしで使える。
- Server Actions（`actions.ts`）と `lib/api/` は `vi.mock` で置き換える。`lib/api/` は `import "server-only"` を含むため、モックせずに読み込むとテストが失敗する。
- `next/navigation`（`useRouter`、`useSearchParams` など）を使うコンポーネントは、`next/navigation` をモックする。

**このプロジェクトの Next.js は学習データより新しい版**なので、Next.js の API（`next/navigation` など）をモックする前に、`apps/web/node_modules/next/dist/docs/01-app/02-guides/testing/vitest.md` と、使っている API のガイドを確認する。

### 5. 実行して確認する

`apps/web` で次を実行する（コンテナが起動していれば `docker compose exec web ...`）。

```sh
bun run test
bun run lint
bun run typecheck
```

- 失敗したテストは、**テストの誤り**か**実装が仕様と違う**かを見分ける。テストの誤り（探し方の間違い、非同期の待ち忘れなど）は直す。実装が仕様と違う場合は、テストはそのまま残し、実装は直さずに報告する。
- Lint・型チェックはテストファイルについて通るまで直す。

### 6. 報告する

次の形で報告する。コミット・プッシュ・PR の作成は、ユーザーに指示されたときだけ行う。

```markdown
## 対象
- 仕様書：`docs/specs/008-visit.md`（ステータス：確定）
- 画面：P-08 訪問記録の登録

## 作成したテスト
| ファイル | 件数 | 確かめていること |
|---|---:|---|
| `features/visit/schemas.test.ts` | 8 | 3章の制約（訪問日・メモの境界値） |
| `features/visit/components/VisitForm.test.tsx` | 4 | SC-008-01〜03、05 |

## 受け入れ基準との対応
| SC | テスト | 結果 |
|---|---|---|
| SC-008-01 | `VisitForm.test.tsx` | 通過 |
| SC-008-03 | `VisitForm.test.tsx` | **失敗**（実装が仕様と違う。下記） |

## 実装が仕様と違う点
- SC-008-03：仕様では「未来の日付はエラー」だが、`visitSchema` に日付の上限がなく登録できてしまう。

## 書けなかった受け入れ基準
- SC-008-04（Unit）：削除の確認ダイアログが未実装のため。

## 確認結果
- テスト：12件中11件通過（1件は上記の仕様との違い）
- Lint：通過
- 型チェック：通過
```

「実装が仕様と違う点」「書けなかった受け入れ基準」がない場合も「なし」と書く。ユーザーが実装や仕様書を直すべきか判断する材料になるため。
